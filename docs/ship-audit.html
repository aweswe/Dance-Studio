RHYTHMZZ SHIP AUDIT

A deep audit of the Rhythmzz Academy platform across four surfaces — public site, student & auth, admin portal, and engineering — with one question: what stands between today's app and a genuinely high-end product?

The foundation is unusually strong. What blocks shipping is not polish.

The team built a real design system, a properly guarded action layer, and genuinely thoughtful SEO. But the three flows a studio lives on — students logging in, fees being collected, and the site showing real dancing — don't function end-to-end yet. Fix the seven P0s and the launch is credible; everything after that is passing the bar.

What's genuinely good

Fundamental gaps

P0 = blocks trust or launch · P1 = daily trust & ops · P2 = polish & hygiene
P0

Most real students can never log in

Account provisioning is broken for the dominant enrolment channel. students.auth_id is only ever written by the dormant Razorpay fulfilment path. Students enrolled offline or via WhatsApp get auth_id = NULL, so OTP login creates an identity, finds no row, and silently redirects the parent back to the marketing homepage with zero explanation. There is no admin "invite to portal" flow anywhere.

Fix: admin "Enable portal access" action per student — create auth user by phone, write auth_id, fire the enrolment_welcome WhatsApp template (already defined). Plus a "number not recognized — we'll help" recovery state on the login page.

P0

Anyone can read revenue and any student's attendance via the API

Data leak through public RPCs. get_dashboard_analytics() and get_student_attendance_summary() are SECURITY DEFINER functions with default PUBLIC EXECUTE — no REVOKE anywhere in setup.sql. PostgREST exposes them anonymously: revenue, occupancy, active counts, and any student's attendance history by UUID, all bypassing RLS.

Fix: REVOKE EXECUTE ... FROM PUBLIC and grant to authenticated with role checks inside the functions.

P0

Any logged-in student can delete the studio's gallery

Storage policies grant every authenticated user INSERT/UPDATE/DELETE on the gallery bucket. The isAdmin check in uploadMedia protects only the app's own UI — calling the storage API directly with any session bypasses it. Gallery vandalism and free file hosting for anyone with a student account.

Fix: admin-only storage policies; keep public SELECT.

P0

Payments are 100% offline — and the dormant path is broken anyway

No money moves through the product. Razorpay routes exist but nothing calls them, payment_orders RLS would deny anonymous writes (create-order would 500), and the webhook is unconfigured. Every fee is collected out-of-band and logged by hand, and the fee status is a binary month check that shows "you owe ₹2,500" even when Paid — advance payments are invisible to the model.

Fix: a month-allocated fee ledger first (each payment names the month it covers), then wire Razorpay properly — RLS policy, webhook, and a real Pay button on the student fees page.

P0

Zero rate limiting anywhere

OTP login, password login, anonymous rental inserts, and broadcast have no throttling. The WhatsApp OTP channel costs per send, the rental API is anonymous (WITH CHECK (true)), and broadcast can be spammed — spam and bill abuse, full stop.

Fix: in-memory or Upstash rate limits on the OTP/verify/login endpoints, rental form, and broadcast action.

P0

No deploy, no CI, no tests, no migration workflow

The product lives only on localhost. No Vercel config, no .github/, zero test files, and the schema is a hand-pasted setup.sql that has already drifted from the backup folder (instructors.role exists only in setup.sql). Supabase's managed daily backups are adequate; everything else is unversioned.

Fix: deploy to Vercel with the custom domain, add a CI smoke build, and move the schema to supabase/migrations with the CLI.

P0

The flagship section of the homepage renders empty

Zero photography anywhere. The live gallery table is empty and all six instructor photo_urls are NULL — so "Class Days & Show Nights" renders a blank grid and every instructor card is a grey letter-avatar. The About page even self-labels its tiles "stand-ins for studio photography". For a dance studio this reads as "we don't exist".

Fix: shoot or seed 20–40 real photos plus instructor headshots through the (already built) gallery manager, and swap the generic OG image for a real one.

P1

Admin daily ops are missing their most-used tools

Six concrete gaps: student search/filter are dead controls (typing does nothing); the first "Load More" duplicates page 1; there's no walk-in enrolment from the admin (the owner must open the public site); no click-to-call or WhatsApp link on any phone number anywhere in admin — for an Indian studio this is the single most-used daily action; fee reminders hit the first 20 students alphabetically regardless of who actually owes; destructive actions (gallery delete, deactivate, rental decline) have no confirmation and gallery errors are swallowed silently.

Fix: tel:/wa.me links on every row (20 minutes), wire search + seed the pagination cursor, add an Add-Student modal, a due-date-driven reminder list, and confirm dialogs.

P1

Every canonical, OG, and sitemap URL points at the wrong domain

rhythmzzdance.com is hard-coded everywhere — metadataBase, sitemap, robots, JSON-LD — while the brand email and admin run on rhythmzz.in. Search engines get the wrong canonical host for every page.

Fix: one SITE_URL constant, and a DNS/redirect decision before launch.

P1

WhatsApp sends are silently mocked

No WHATSAPP_API_KEY is configured, so broadcasts, fee reminders, and rental confirmations all "succeed" while sending nothing. Deferring Razorpay was a product decision; silent no-op sends are a trap — the owner will believe 200 parents were messaged.

Fix: live WhatsApp Business API key (WATI/Interakt), plus a visible "MOCK MODE" banner in admin when the key is absent.

P1

The enrolment funnel ends in a broken promise

The final button says "Confirm & Pay" unconditionally, but payments are deferred — visitors walk a 3-step form expecting payment and hit "Online payments are coming soon". Also: no enquiry form on the Contact page (only links), so leads who won't open WhatsApp leave nothing behind.

Fix: rename the button to "Confirm Booking" when payments are disabled, and add a one-field callback-request form on Contact.

P1

Student-side trust details erode what the portal gets right

Attendance shows 100% for a student with zero records — proudly wrong. Kuchipudi progress is decorative: modules_completed is fetched but never rendered (hardcoded modules instead), and an unknown level string breaks the whole stepper. No profile edit — a parent who changes numbers is locked out until an admin fixes it. Schedule crashes if batch.days is null. Every notice renders as "Academy Notice".

Fix: null-safe attendance % with a "no records yet" state, render real progress data, add a profile page, and per-type notice titles.

P2

Public-site polish debt

Gallery lightbox: div onClick with no keyboard handler, no Esc, no focus trap. The announcement banner, when active, paints over the fixed nav on mobile. Sitemap lastModified is hard-coded to 2026-01-01. Blog pages lack canonicals. public/ still ships create-next-app boilerplate SVGs.

P2

Multi-kid families are impossible

students.phone is UNIQUE and the portal resolves a single auth_id — one parent, one child, siblings need separate phone numbers. For a kids' academy this is a real ceiling on adoption.

Fix (later): family accounts — parent identity resolves to multiple students with a child switcher.

P2

Admin detail gaps

No rental calendar view (it's a list — double-bookings can't be spotted); decline sends no notification to the renter; DB errors collapse into "No students found" (indistinguishable from an empty academy); the dashboard is five number cards with no charts or pending-items feed; no markdown preview in the blog editor; fee table capped at 100 records.

P2

Engineering hygiene

updateProgress is unguarded, unvalidated, swallows errors, and always returns success. Certificate HTML interpolates student.name raw (stored XSS). Homepage fires 7 Supabase queries per request with no caching. Broadcasts send sequentially — 200 recipients exceeds serverless timeouts; no queue or retry. No Sentry/analytics/global-error. README is untouched create-next-app boilerplate.
